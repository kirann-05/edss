## Likely questions

**Why agents at all, instead of a dashboard with SQL?**
The agentic parts are the clarify and plan loop, parallel domain agents, drafting options and risks, self-healing validation and the human gate. The arithmetic is deliberately not agentic, because a KPI that depends on an LLM is a KPI nobody can audit. Honest weakness: the LLM surface is narrow, and a sceptic could say most of this is a pipeline. The answer is that the narrow surface is the design, and the agent loop earns its place in planning, drafting and repair.

**How do you stop it hallucinating numbers?**
The LLM never writes numbers. It is never even given one. It writes reference tokens that a renderer fills in from the KPI engine, and check V1 rejects any digit or spelled-out number it writes itself. Failure injection proves it: eight different faults, including a made-up percentage, are each caught by the intended check and repaired within three attempts, in a test that runs on every commit. `make acceptance` measures it: across 18 plans (every period, every mix of areas) the faults could be applied 94 times, and all 94 were caught first time by the check meant to catch them and repaired. The real local model's nine drafts all passed V1 to V9. Weakness: those are the eight faults we wrote, and the repairs in that report are by the canned model.

**Is it really real-time?**
It is as fresh as each source. The sources are read in batches, on demand from the Refresh data button, and every figure shows the date of its oldest input. Finance may only be quarterly. Data older than 90 days is flagged stale wherever it is used, instead of pretending. Weakness: there is no scheduler yet, and nothing streams from source systems.

**Why LangGraph and not plain Python or CrewAI?**
The book's design needs a bounded back-edge, parallel fan-out, checkpoint and resume, and a human interrupt. LangGraph provides each natively. Plain Python means rebuilding all four. CrewAI is role-centric and makes the approval gate and resume awkward. Weakness: LangGraph's API moves quickly, so versions are pinned.

**Why is the Coordinator not a separate agent?**
Its job is state, plan, budgets and audit. That is control logic, and putting an LLM there adds risk without benefit. It is the graph plus the runtime wrapper.

**What if the LLM drafts a bad option?**
Options are labelled drafts with stated assumptions, risks and trade-offs, cite KPI references, and pass through a human who can edit or override. The system never acts on them.

**What about privacy of university data?**
Aggregated department data first, no personal identifiers requested, local models only for real data, enforced in code against the database setting, no external tracing, role-based access with HOD scoping, hash-chained audit.

**How does it scale to other departments?**
Departments and KPI definitions are data. Sources are adapters. Adding a department is a data change. Honestly, today everything is held in memory, so the first step is the PostgreSQL store. After that, one database and one model server are fine for tens of departments, and the next step would be queueing runs.

**Why did you not do best-of-N like the book's Lab 8?**
Best-of-N makes sense for generated content, not for deterministic KPIs. We parallelise across domains and across KPIs and merge by plan coverage. Best-of-N is optional for option wording only.

**How do you know it works?**
964 backend tests, 224 component tests and 15 browser tests, all passing. Within those: ten planted traps with exact expected values, the eight injected faults, and a browser test of approve, publish and rollback. `make rehearse` walks the whole demo in a browser in about nine seconds and fails if any step breaks. Parallelism is measured from each run's own events and shown on screen. `make acceptance` adds 94 fault trials over 18 plans, all caught and repaired, and 18 of 18 clean drafts passing first time. Not built yet: a separate parallel benchmark script.

**Are the KPIs the real NIRF and NAAC ones?**
Only once IQAC supplies approved definitions. Until then the seed definitions are marked placeholders, and the system is built so swapping them is a data change. Say this plainly.

**How do you know a HOD cannot see another department?**
Because the response does not contain it. A restricted department row carries its name and nothing else. A test signs in as a HOD, reads the raw JSON of the drill-down, domain and data-health responses, and checks that no other department's value, input or fact id is present, with a positive control proving the check can find them. A second test walks the route table, so a route added later that forgets to check the session fails on its own.

**What happens when a department has no data, or only unreconciled data?**
It is left out of that KPI and said so, in words, next to the figure. It is never counted as zero. The drill-down lists the unreconciled record with its badge and marks it as not used. This is deliberately strict (D24). The cost is that one unreconciled figure removes a department from a KPI, and the alternative of summing the final quarters only would risk an apples to oranges ratio.

**How do you stop an approver from publishing something the checks rejected?**
The approve button is a convenience, the rule is in the governance service. It recomputes the brief's validation state on every decision. If the draft was escalated and any integrity check (V1, V4, V5, V6, V7, V9) is still failing, approval is refused with the reason and the refusal is written to the audit log. Completeness failures (V2, V3, V8) can be approved only with an explicit acknowledgement that is stored with the approval. This is a reading of rule 10 that Kiran confirmed (D13): a draft that failed an integrity check can never be approved.

**What happens if the server dies halfway through a run?**
Every node writes a checkpoint, and a resume starts from the last one without redoing finished work. A test crashes a node once and checks the finished agents do not run again. Weakness: the checkpointer is in memory for now, so this holds across a crash of one run, not a restart of the server, until the Postgres checkpointer exists.

**What is the weakest part?**
The planner on a small local model. Measured on this laptop, it asked exactly the right questions for only 4 of 10 requests, and when it planned, 4 of 6 plans were fully right. The safeguard is that a person reviews and edits every plan before anything runs, and the steps of the plan are built in code, not by the model. The other honest weaknesses, in order: everything is in memory, so a restart loses runs, versions and the audit log until PostgreSQL is in; the connector is an in-process interface, not yet the MCP server, so the "one door" is enforced by a test on imports rather than a process boundary; and no real data or official KPI definitions have arrived, so the traps are my guess at what real data gets wrong.

**Why does the demo use canned drafts instead of the model?**
Speed and repeatability. On this MacBook Air the 4 billion parameter model takes about 28 seconds per option draft, so a full brief takes minutes. The canned model follows exactly the same path through the graph and the same nine checks. The real model works and is measured in `docs/evals`. In production it runs on the university's GPU server, whose specification is still awaited.

**Is the model evaluation fair?**
It is small and I say so: ten planning requests and nine drafts, one run each, with the expected answers labelled by me. To avoid marking the model on its own homework, the worked examples in the prompts use different requests from the ones it is scored on. The rule-based baseline scores 9 of 10 and 6 of 6, which shows the requests are answerable.

**What did you need from the university, and what is still missing?**
Real exports with a signed data specification, the IQAC's official KPI definitions and targets, the GPU server's specification, hosting, and real user accounts. The full list is in `docs/PENDING.md`. Nothing in the agents, the engine or the screens changes when they arrive: real data goes in through the same ingestion path, with a reconciliation report for the data owner.

## Component notes

| Component | What it is | Why this choice | Rejected alternative | Known weakness |
| --- | --- | --- | --- | --- |
| KPI engine | Decimal-only engine. A KPI formula is YAML data, parsed with Python's own parser and checked against an allow-list (no eval). It computes one value per department and one for the institution, from totals, and decides status on the unrounded value | Auditable and reproducible: a figure never depends on a model. Tests carry the planted traps with exact expected values | Letting an LLM compute KPIs, or evaluating formulas with eval | A department is kept out of a KPI if any input it needs is missing or not final, so one unreconciled figure removes that department from that KPI (D24). `period_agg` and the 2 percent at-risk band are my defaults, not IQAC's. Citations can double count shared papers (D23) |
| Connector | One `Connector` interface is the only way an agent reads data: facts, publications, sources, KPI definitions, targets, periods. `InMemoryConnector` implements it over the data store, and a scope registry stands in for the Registrar's per-domain authorisation, checked before any data is read | Rule 6. An agent cannot be talked into reading what it has no function for, and swapping the stand-in for a real MCP server is a one-file change | Agents querying the database or opening files directly, guarded only by a line in the prompt | It runs in the same process, so there is no network boundary, token expiry or per-call credential yet (spike G2). The test that enforces it is a static import check, so a dynamic import would slip past it |
| Ingestion | CSV and read-only SQL adapters read a source into canonical columns, a validator refuses any row that breaks the data contract with a plain reason and counts it, a ledger holds immutable batches (the same content again adds nothing, a changed file is a new batch, superseded records are kept), a manifest names the files, and a reconciliation report shows a data owner what came in, what was refused and where there is no record. A refresh reads the folder again into the same ledger | Real data will arrive in unknown columns and unknown quality. The adapters are the only thing that changes, and a test proves a CSV source and a SQL source give identical KPIs to the original in every period | Reading files straight into the engine, or silently correcting bad rows | Only the synthetic set has been through it, so how a real extract behaves is untested. The SQL read-only guard is a second line of defence, the first is a database account that can only read. Excel files are not read, they must be saved as CSV. Loading into Postgres is not built |
| Graph | A LangGraph graph: plan lock, access check, four domain agents in parallel, KPI synthesis, option drafting in parallel for each off-target KPI, report compose, validate with a bounded repair loop, prepare the gate, human gate, finish. The coordinator is this graph plus a wrapper that records every step, not a separate model | The design needs fan-out, a bounded back-edge, checkpoint and resume, and a human interrupt, and LangGraph has each natively | A plain Python loop, which means rebuilding all four, and CrewAI, where an approval gate and resume are awkward | The checkpointer is in memory, so a server restart loses runs that have not reached the gate. Domain agents read a local store, so parallel gain is small unless sources are slow (D19), the demo uses a labelled simulated latency. Only option drafting is model work, so the agentic surface is narrow on purpose |
| LLM layer | One chat model interface. A canned rule-based model for tests and the demo fallback, and a real client for an OpenAI-compatible server (Ollama in development, vLLM later) that asks for output constrained by a JSON schema with thinking switched off. Prompts are data in one file and carry the rules. A cheap code-side check gives the model specific feedback before the gate, with a different random seed on each repair. A data-mode guard refuses a hosted model for real data by provider name and by host, at construction and on every call | Rules 1 and 7, and measured reliability. The model is never given a figure and can only refer to one by token | Trusting the provider name alone, asking a model to write the outline steps, or measuring by feel | Measured with `qwen3.5:4b` (docs/evals): drafts pass the full gate 9 of 9 with no repair, but the planner asks the right questions only 4 of 10 times and plans fully right 4 of 6, against 9 of 10 and 6 of 6 for the rule-based baseline I wrote. One run each, labels are mine. A person reviews the plan and the drafts, so a miss costs a click |
| Validation gate | Nine pure checks (V1 to V9) over the whole draft, each returning violations with a locator and a fix hint. V1 rejects any digit or spelled-out number outside a token and any figure with no source. A repair step rebuilds only the failing part, the graph allows three attempts, then escalates with a diagnosis. Eight faults can be injected, and a test per fault proves the intended check catches it and the repair clears it | Rule 10, and a claim that can be measured rather than asserted | Asking the LLM to review its own draft, or one regex for everything | V1 proves numbers arrive by reference, not that the prose around them is true. A sentence saying "improved" beside a falling KPI is caught only by V4's keyword check, which is brittle (D21). `make acceptance` catches 94 of 94 applicable fault trials over 18 plans with the intended check, but those are the eight faults we wrote |
| Human gate | The graph stops at an interrupt, with nothing that has a side effect before it, and the graph has no publish step at all. A person decides through the governance service, which checks their role, and only a successful decision resumes the graph. Escalated drafts reach the person, but Approve is blocked past an integrity failure (V1, V4, V5, V6, V7, V9), and completeness failures (V2, V3, V8) need an explicit acknowledgement | Rule 2. Approval is a different code path from the agent, so no prompt can reach it. Rule 10 stays true because a draft that failed an integrity check can never be approved | A confirm step inside the agent, or letting an exhausted retry publish | No separation of duties, the person who started a run can approve it if their role allows. Decisions resume on the in-memory checkpointer. D13 is a reading of rule 10, confirmed by Kiran |
| Versioning and rollback | Each approval writes an immutable version, a pointer says which one is current, and rollback moves the pointer to an earlier version with a reason, never deleting anything. Any two versions can be compared field by field, and an approver's edits are kept against the draft they changed | Rule 2 and a history leadership can read: what was current on a given day, who approved it, what was edited | Overwriting in place, or deleting newer versions on rollback | In memory, so a restart loses the versions until the Postgres store exists (F3). Edits cannot contain digits, only tokens, which is safe but means an approver cannot type a new figure |
| Audit chain | Every step and every refusal appends a row. Each row's hash covers the previous row's hash and a canonical form of its content, so a verifier can recompute the chain and name the first row that does not match. One writer at a time, tested under eight concurrent threads | Rule 9. The chain makes tampering detectable, and the canonical form means the same content always hashes the same | A plain log table, or a blockchain, which adds nothing here | A hash chain detects tampering, it does not prevent it. Someone who can rewrite the whole table and recompute every hash would go unnoticed unless the head hash is kept elsewhere. Rows keep a short readable summary and a hash of the full payload, not the payload. The append-only database role (F4) and the Postgres advisory lock are not built |
| RBAC | A permission matrix written out from SPEC section 2, plus a department scope. Scope is applied in one place, the view builders, so a restricted department row carries its identity and nothing else | The guarantee has to hold in what is sent, not in what the UI chooses to draw. A test reads raw response bodies as a HOD and a generic test walks every route | Hiding data in the UI only, or ad hoc checks in each route | Users are in memory with one shared synthetic password. | Login and sessions | Five failed sign-ins in fifteen minutes lock that email for fifteen minutes, per email so a shared campus address is not locked out. A session carries a version, so a password reset or switching someone off ends every session they had at once | Guessing passwords is the first thing anyone tries, and a removed person must lose access immediately | Locking by network address, or waiting for a token to expire | The counts are in one process, so a restart forgets them and several servers would each keep their own.
