## Likely questions

**Why agents at all, instead of a dashboard with SQL?**
The agentic parts are the clarify and plan loop, parallel domain agents, drafting options and risks, self-healing validation and the human gate. The arithmetic is deliberately not agentic, because a KPI that depends on an LLM is a KPI nobody can audit. Honest weakness: the LLM surface is narrow, and a sceptic could say most of this is a pipeline. The answer is that the narrow surface is the design, and the agent loop earns its place in planning, drafting and repair.

**How do you stop it hallucinating numbers?**
The LLM never writes numbers. It writes reference tokens that a renderer resolves from the database, and check V1 rejects any stray digit. Failure injection proves it: we inject a fake figure and the gate catches it. Cite the measured detection rate.

**Is it really real-time?**
It is as fresh as each source. Ingestion runs on a schedule and on demand, and every figure shows an as-of date. Finance may be quarterly. We flag stale data instead of pretending. Weakness: no streaming from source systems.

**Why LangGraph and not plain Python or CrewAI?**
The book's design needs a bounded back-edge, parallel fan-out, checkpoint and resume, and a human interrupt. LangGraph provides each natively. Plain Python means rebuilding all four. CrewAI is role-centric and makes the approval gate and resume awkward. Weakness: LangGraph's API moves quickly, so versions are pinned.

**Why is the Coordinator not a separate agent?**
Its job is state, plan, budgets and audit. That is control logic, and putting an LLM there adds risk without benefit. It is the graph plus the runtime wrapper.

**What if the LLM drafts a bad option?**
Options are labelled drafts with stated assumptions, risks and trade-offs, cite KPI references, and pass through a human who can edit or override. The system never acts on them.

**What about privacy of university data?**
Aggregated department data first, no personal identifiers requested, local models only for real data, enforced in code against the database setting, no external tracing, role-based access with HOD scoping, hash-chained audit.

**How does it scale to other departments?**
Departments and KPI definitions are data. Sources are adapters. Adding a department is a data change. What changes at larger scale: a single node database and one LLM server, which is fine for tens of departments, and the next step would be queueing runs and caching.

**Why did you not do best-of-N like the book's Lab 8?**
Best-of-N makes sense for generated content, not for deterministic KPIs. We parallelise across domains and across KPIs and merge by plan coverage. Best-of-N is optional for option wording only.

**How do you know it works?**
The acceptance suite (checks V1 to V9), the planted-trap fixtures with exact expected values, the failure injection suite, the parallel benchmark, and an end-to-end test of approve, publish and rollback.

**Are the KPIs the real NIRF and NAAC ones?**
Only once IQAC supplies approved definitions. Until then the seed definitions are marked placeholders, and the system is built so swapping them is a data change. Say this plainly.

**How do you know a HOD cannot see another department?**
Because the response does not contain it. A restricted department row carries its name and nothing else. A test signs in as a HOD, reads the raw JSON of the drill-down, domain and data-health responses, and checks that no other department's value, input or fact id is present, with a positive control proving the check can find them. A second test walks the route table, so a route added later that forgets to check the session fails on its own.

**What happens when a department has no data, or only unreconciled data?**
It is left out of that KPI and said so, in words, next to the figure. It is never counted as zero. The drill-down lists the unreconciled record with its badge and marks it as not used. This is deliberately strict (D24). The cost is that one unreconciled figure removes a department from a KPI, and the alternative of summing the final quarters only would risk an apples to oranges ratio.

**How do you stop an approver from publishing something the checks rejected?**
The approve button is a convenience, the rule is in the governance service. It recomputes the brief's validation state on every decision. If the draft was escalated and any integrity check (V1, V4, V5, V6, V7, V9) is still failing, approval is refused with the reason and the refusal is written to the audit log. Completeness failures (V2, V3, V8) can be approved only with an explicit acknowledgement that is stored with the approval. Weakness: this changes what rule 10 literally says, so it needs Kiran's confirmation (D13).

**What happens if the server dies halfway through a run?**
Every node writes a checkpoint, and a resume starts from the last one without redoing finished work. A test crashes a node once and checks the finished agents do not run again. Weakness: the checkpointer is in memory for now, so this holds across a crash of one run, not a restart of the server, until the Postgres checkpointer exists.

**What is the weakest part?**
Update this with the truth as the build proceeds. Initial candidates: small local models and structured output reliability, dependence on how clean the university's data is, and the placeholder KPI definitions.

| KPI engine | Decimal-only engine. A KPI formula is YAML data, parsed with Python's own parser and checked against an allow-list (no eval). It computes one value per department and one for the institution, from totals, and decides status on the unrounded value | Auditable and reproducible: a figure never depends on a model. Tests carry the planted traps with exact expected values | Letting an LLM compute KPIs, or evaluating formulas with eval | A department is kept out of a KPI if any input it needs is missing or not final, so one unreconciled figure removes that department from that KPI (D24). `period_agg` and the 2 percent at-risk band are my defaults, not IQAC's. | Connector | One `Connector` interface is the only way an agent reads data: facts, publications, sources, KPI definitions, targets, periods. `InMemoryConnector` implements it over the data store, and a scope registry stands in for the Registrar's per-domain authorisation, checked before any data is read | Rule 6. An agent cannot be talked into reading what it has no function for, and swapping the stand-in for a real MCP server is a one-file change | Agents querying the database or opening files directly, guarded only by a line in the prompt | It runs in the same process, so there is no network boundary, token expiry or per-call credential yet (spike G2). The test that enforces it is a static import check, so a dynamic import would slip past it |
| Ingestion | Only the synthetic generator exists so far: deterministic (seed 42), calibrated to exact totals, with ten planted traps and one test each | The demo and the tests need known answers, so the data is built to have them | Random data with no traps, which would prove nothing | It is not real data, and its dates are relative to the day it is seeded, so it goes stale after 90 days until re-seeded. Real adapters, validation and rejection counts are still to build (F2) |
| Graph | A LangGraph graph: plan lock, access check, four domain agents in parallel, KPI synthesis, option drafting in parallel for each off-target KPI, report compose, validate with a bounded repair loop, prepare the gate, human gate, finish. The coordinator is this graph plus a wrapper that records every step, not a separate model | The design needs fan-out, a bounded back-edge, checkpoint and resume, and a human interrupt, and LangGraph has each natively | A plain Python loop, which means rebuilding all four, and CrewAI, where an approval gate and resume are awkward | The checkpointer is in memory, so a server restart loses runs that have not reached the gate. Domain agents read a local store, so parallel gain is small unless sources are slow (D19), the demo uses a labelled simulated latency. Only option drafting is model work, so the agentic surface is narrow on purpose |
| LLM layer | One chat model interface with a rule-based FakeLLM for development and tests, a client for OpenAI-compatible endpoints, and a structured call that checks the answer against a schema and retries inside a budget. A data-mode guard refuses a hosted model when the data is real, by provider name and by base URL host, at construction and again on every call by reading the live mode | Rules 1 and 7. The guard has to hold even when the provider is called something harmless but points at a remote host, and even when the mode is flipped after a model exists | Trusting the provider name alone, or reading the mode once at start | Only the FakeLLM has run. Whether a small local model fills the structured outputs reliably is untested until Day 4, and the FakeLLM writes from templates, so demo wording will read better than a real model's |
| Validation gate | Nine pure checks (V1 to V9) over the whole draft, each returning violations with a locator and a fix hint. V1 rejects any digit or spelled-out number outside a token and any figure with no source. A repair step rebuilds only the failing part, the graph allows three attempts, then escalates with a diagnosis. Eight faults can be injected, and a test per fault proves the intended check catches it and the repair clears it | Rule 10, and a claim that can be measured rather than asserted | Asking the LLM to review its own draft, or one regex for everything | V1 proves numbers arrive by reference, not that the prose around them is true. A sentence saying "improved" beside a falling KPI is caught only by V4's keyword check, which is brittle (D21). A detection rate over many random drafts is not measured yet |
| Human gate | The graph stops at an interrupt, with nothing that has a side effect before it, and the graph has no publish step at all. A person decides through the governance service, which checks their role, and only a successful decision resumes the graph. Escalated drafts reach the person, but Approve is blocked past an integrity failure (V1, V4, V5, V6, V7, V9), and completeness failures (V2, V3, V8) need an explicit acknowledgement | Rule 2. Approval is a different code path from the agent, so no prompt can reach it. Rule 10 stays true because a draft that failed an integrity check can never be approved | A confirm step inside the agent, or letting an exhausted retry publish | No separation of duties, the person who started a run can approve it if their role allows. Decisions resume on the in-memory checkpointer. D13 changes the meaning of rule 10 and waits for Kiran's yes |
| Versioning and rollback | Each approval writes an immutable version, a pointer says which one is current, and rollback moves the pointer to an earlier version with a reason, never deleting anything. Any two versions can be compared field by field, and an approver's edits are kept against the draft they changed | Rule 2 and a history leadership can read: what was current on a given day, who approved it, what was edited | Overwriting in place, or deleting newer versions on rollback | In memory, so a restart loses the versions until the Postgres store exists (F3). Edits cannot contain digits, only tokens, which is safe but means an approver cannot type a new figure |
| Audit chain | Every step and every refusal appends a row. Each row's hash covers the previous row's hash and a canonical form of its content, so a verifier can recompute the chain and name the first row that does not match. One writer at a time, tested under eight concurrent threads | Rule 9. The chain makes tampering detectable, and the canonical form means the same content always hashes the same | A plain log table, or a blockchain, which adds nothing here | A hash chain detects tampering, it does not prevent it. Someone who can rewrite the whole table and recompute every hash would go unnoticed unless the head hash is kept elsewhere. Rows keep a short readable summary and a hash of the full payload, not the payload. The append-only database role (F4) and the Postgres advisory lock are not built |
| RBAC | A permission matrix written out from SPEC section 2, plus a department scope. Scope is applied in one place, the view builders, so a restricted department row carries its identity and nothing else | The guarantee has to hold in what is sent, not in what the UI chooses to draw. A test reads raw response bodies as a HOD and a generic test walks every route | Hiding data in the UI only, or ad hoc checks in each route | Users are in memory with one shared synthetic password. No login lockout, no SSO. The demo sign-in exists only in synthetic mode and is covered by a test, but it is a deliberate bypass of passwords |
| Dashboard | Next.js against the real API, with types generated from its OpenAPI contract. Every status is an icon plus a label. Figures are exact decimal strings rounded by the UI with BigInt, and a missed target that rounds to equal is called out in words | Rules 4 and 5 made visible, and a contract that cannot drift quietly (D22) | The Streamlit prototype from Labs 1 and 2, which cannot do roles, a review queue or an audit view, and a mock API inside the browser | Light theme only, no axe or Playwright run yet, ECharts bundle size not measured, and it still runs against the in-memory synthetic store rather than Postgres |
